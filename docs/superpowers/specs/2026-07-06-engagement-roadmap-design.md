# チーム定着・楽しさ向上ロードマップ

日付: 2026-07-06
ステータス: ロードマップ確定(各機能の詳細設計は実装着手時に個別に行う)

## 背景と目的

Scrum Owl の主力機能は Planning Poker と Rotate。現状のボット出力は事務的で、
「Scrum Owl」という名前とロゴ以外にキャラクター性がない。また Poker のセッション
結果はメモリ上にしか存在せず、チームの見積もり傾向を振り返る手段がない。

本ロードマップの狙いは **チームへの定着と使う楽しさの向上**。方向性は次の2軸:

1. **キャラ・世界観** — フクロウの人格化でボットに愛着を持たせる
2. **統計・振り返り** — 蓄積データを見せてレトロスペクティブの材料にする

## 採用機能

### 1-3. フクロウ状況リアクション(Poker連動)

投票公開時に票の内容へフクロウが反応する。

- 全員一致 → 祝福(例: 「ホホゥ、息ぴったりだね!」)
- 票が大きく割れた(例: 2 と 13 が混在)→ 「ホゥ? 話し合いが必要そうだね」

票のバラつき計算ロジックはセッション内で完結し、永続化は不要。
このバラつき計算は Phase 2 の統計機能(2-2)で再利用する。
UX 上のポイント: 装飾ではなく「見積もりの割れ」という意味のある情報を
キャラ経由で伝えること。

### 2-4. `/rotate template stats` — 当番の公平性表示

テンプレートが既に永続化している `selectionCounts` を表示するサブコマンド。

- メンバーごとの選出回数(例: Alice 5回、Bob 3回)
- 今の巡でまだ選ばれていない人(袋の残り)も示す

注記: 選択アルゴリズムはシャッフルバッグ方式へ変更予定
(2026-07-06-rotate-shuffle-bag-design.md 参照)。重み表示ではなく
袋の残りを表示する。

追加のデータ収集は不要。既存データを見せるだけのクイックウィン。

### 2-1. セッション履歴の永続化(基盤)

Poker セッション終了時に結果を `data/poker-history.json` へ保存する。

- 保存内容: 議題、各参加者の票、平均、日時、チャンネル/ギルドID
- 実装は既存ストレージパターン(`ReminderStorage` と同型)を踏襲した
  `PokerHistoryStorage` を追加
- 単体では地味だが、2-2 / 2-5 / 1-5 すべての土台

### 2-2. `/poker stats` — チーム見積もり統計

永続化された履歴から直近 N セッションの統計を表示する。

- 合意率(票の一致度)の推移
- 平均バラつき
- セッション数の推移

「チームの息が合ってきた」を可視化し、レトロスペクティブの材料にする。

### 2-5. 週次ダイジェスト(フクロウ便り)

週1回、フクロウが指定チャンネルに1週間のまとめを投稿する。

- 例: 「今週は見積もり4回、合意率の平均82%、ファシリテーター最多は Alice」
- 配信基盤は `ReminderScheduler` の1分 tick を流用
- 統計を「見に行く」から「届く」に変える定着装置

### 1-5. フクロウの巣(サーバー成長要素)

チームの活動量(セッション数・投票数など)でサーバーごとのフクロウが成長する。

- `/owl` コマンドで巣の状態を表示
- 活動ログ(2-1 の履歴永続化)が前提
- 世界観の集大成として最後に実装

## ロードマップ

### Phase 1: クイックウィン(基盤不要、各1〜2日規模)

| 機能                         | 理由                                                  |
| ---------------------------- | ----------------------------------------------------- |
| 2-4 `/rotate template stats` | 既存 `selectionCounts` を表示するだけ。追加データゼロ |
| 1-3 フクロウ状況リアクション | セッション内で完結、永続化不要                        |

### Phase 2: 統計基盤(数日〜1週規模)

| 機能                       | 理由                                                       |
| -------------------------- | ---------------------------------------------------------- |
| 2-1 セッション履歴の永続化 | Phase 2 以降すべての土台                                   |
| 2-2 `/poker stats`         | 永続化と同時期に出し、データが貯まる期間を待ち時間にしない |

### Phase 3: 定着装置(各1週前後)

| 機能                 | 理由                                     |
| -------------------- | ---------------------------------------- |
| 2-5 週次ダイジェスト | 履歴データが貯まってから意味を持つ       |
| 1-5 フクロウの巣     | 最大の作り込み。活動ログ必須。最後に実装 |

### 順序の設計意図

- **「見せる前に貯める」** — 履歴永続化(2-1)を早く入れるほど後続機能の
  データが充実する
- Phase 1 で日々の体験が先に良くなる → チームが使い続ける →
  Phase 2-3 のデータが自然に貯まる、という循環
- 各 Phase は独立してリリース可能。途中で方針転換しても無駄が出ない

### 依存関係

```
2-4 (rotate stats)      ← 依存なし
1-3 (フクロウ反応)      ← 依存なし(バラつき計算は 2-2 と共有)
2-1 (履歴永続化)        ← 基盤
 ├─ 2-2 (poker stats)
 ├─ 2-5 (週次ダイジェスト)
 └─ 1-5 (フクロウの巣)
```

## 見送った案(検討済み)

| 案                                           | 見送り理由                                                  |
| -------------------------------------------- | ----------------------------------------------------------- |
| 1-1 フクロウのセリフシステム(全コマンド共通) | 今回は採用見送り。1-3 で局所的に導入し、反応を見て拡大判断  |
| 1-2 抽選ドラムロール演出                     | 採用見送り                                                  |
| 1-4 時間帯・季節挨拶                         | 小ネタ。優先度低                                            |
| 2-3 合意度スコア「息ぴったり度」の表示       | スコア表示は見送り。内部のバラつき計算のみ 1-3 / 2-2 で使用 |
| 2-6 見積もり vs 実績の振り返り               | 運用負荷が高く定着率が低いと判断。優先度低                  |

## 進め方

各 Phase の実装着手時に、その機能単位で個別に設計(brainstorming)→
実装計画(writing-plans)→ TDD 実装のサイクルを回す。本書はその親となる
優先順位の合意文書。
